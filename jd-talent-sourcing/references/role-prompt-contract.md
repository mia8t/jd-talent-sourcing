# 独立岗位 Prompt：生成、隔离与更新契约

## 三层边界

- 基础 Skill：维护生成格式、初始化业务默认、核验与授权流程，不存具体岗位配置或候选人材料。
- 岗位 Prompt：每个 role_id 对应独立文档及版本，包含该岗位全部有效筛选标准；文档内的“通用硬筛”是该岗位的标准快照，不是动态引用基础默认。
- 运行记录：保存该岗位某批次目标、候选人、进度及恢复位置；不得反向改写岗位标准或基础 Skill。

初始化时将通用配置模板、JD及本岗位已确认回答合并为完整Prompt；业务取值来自使用者授权配置，不预置企业政策。记录实际采用的规则来源及配置版本，仅供运行资源内追溯，不作为每次运行时动态合并的指针。不自动复制其他岗位的负责人、例外、资源或授权。基础默认以后改变时，只对以后初始化的新岗位生效；已有岗位不自动迁移。若明确要求把新默认应用到指定已有岗位，逐岗位展示差异、取得对应确认并分别更新，不能称修改默认已自动更新全部岗位。

岗位“通用硬筛”的年限、学校或公司背景等可配置业务项发生变化，只更新目标岗位对应条目。所有锁定者不推荐、未知不算通过、授权及写入回读等执行闸门仍适用，不能以岗位例外绕过；冲突时指出具体条目并停止受影响操作。

## 完整文档生成

给出 JD 后自动形成初稿；集中补缺后，将回答合并入同一完整 Prompt。用户不必每次选择版式或自己拼接回答。标准确认必须能看到全部有效条目；获得文档保存授权后创建/更新并回读。配置确认、远程保存和执行授权分别判断，遵循主文边界。

固定顺序如下，正文以可直接交给招聘人员或其他 AI 的执行指令表达：

1. **岗位与任务**：岗位名称、稳定 role_id、Prompt 版本/确认状态、业务目标、本人职责、适用范围。区分常规执行目标与本轮明确目标；明确是有效核验人数还是合格推荐人数，不把一轮数量要求自动变成永久默认。
2. **通用硬筛 G1～Gn**：展开该岗位已采用的学历、总工作年限、公司/垂直背景、锁定、备注意向、历史面评和重复规则等完整有效内容，按实际配置纳入。每条标来源及本岗位例外。
3. **岗位硬筛 H1～Hn**：从 JD/补充回答形成可核验本人能力，逐条写实际职责、经验年限、证据和反例；不得仅放 JD 摘要。通用总工作年限与岗位限定经验分别列出并同时核验。
4. **软筛 S1～Sn 与加分/分级**：逐条写命中证据，独立列出推荐最低门槛及 A/B/C 条件；加分不能补偿硬筛失败，不以近义词凑独立命中。
5. **检索与核验**：本岗位具体标签条件及验证要求、关键词分轮计划、详情顺序、明确淘汰/待核验/通过节点、历史去重与变化比较规则。关键词不能证明通过。
6. **结果、授权与停止**：可用输入/目标资源、输出字段、证据格式、独立人数定义、目标/上限、停止与不足报告、禁止操作、失败恢复。资源未绑定或能力未核实时明示缺口，不制造标识或宣称已能执行。

每条标准独立分行，采用以下统一结构；可用分区表格，但长证据/反例用紧随条目的子项，不挤进长单元格：

- **G/H/S编号｜标准名称**：明确范围、运算符、上下限及是否含边界。
  - 判断依据：材料来源、本人动作、时间计算或状态证据。
  - 去留/命中：满足、不满足、真实读取缺失或矛盾分别怎样处理；正常完整读取后缺必需能力证据按该硬筛不满足，不一概标读取阻塞。
  - 来源与例外：JD、用户已确认、初始化默认或未确认建议；岗位覆盖后呈现有效值，旧值只进变更记录，不并列成两个有效标准。

初稿可以标待确认；最终确认版不得把决定去留的未决项冒称确定。Prompt 内不使用“按 Skill 默认”“参考前文对话”“见其他岗位规则”等外部依赖，所需业务标准、证据、分级、计数和执行边界必须展开。独立使用仍需要执行者拥有合适工具与资源权限；不承诺文本自动取得登录/数据能力。工具特定命令、浏览器一次性引用和候选人运行材料不放入可交接 Prompt。

文档正文是唯一有效配置；变更历史及运行状态与正文明确分区，不混入筛选条目。确认展示使用同一份正文，不另存可能漂移的第二套摘要标准。可以附 JD 来源和简短变更记录以便追溯。

## 更新范围判定

| 用户意图 | 允许修改 | 必须保持不变 |
|---|---|---|
| 修改岗位甲 Prompt，包括其“通用标准” | 甲的对应标准、受影响检索/核验表达及甲版本 | 基础 Skill、乙等其他 Prompt、旧批及人工结果 |
| 本轮临时按另一条件运行 | 本轮授权运行快照及台账 | 甲持久 Prompt、基础 Skill、其他岗位 |
| 明确修改基础 Skill 默认 | 基础默认及必要生成逻辑 | 所有已生成岗位 Prompt；不自动迁移 |
| 明确给多个指定岗位应用变更 | 逐个指定 Prompt，分别确认/回读及版本 | 未指定岗位、基础默认（除非也明确要求） |

“通用标准”这个词不代表全局更新权限。目标唯一且上下文明确时直接定位；多岗位且目标不明确时只问目标岗位。不得以最近打开文档、相同标题或相同负责人猜绑定。

## 局部更新与执行验收

1. 从授权文档/元数据核对目标 role_id、Prompt 文档及最新已确认版本，建立本次允许写入的目标范围；无可靠绑定先解资源缺口。
2. 读取完整有效配置，保存实际可恢复前版/历史引用。只修改明确条目和必要联动，将业务改动与格式改动分别列出，未改变条目原样保持。
3. 在目标 Prompt 内局部写入并回读：核对生效值、上下限、来源、关联经验规则、分级及版本。失败保留最后可验证版本，不用本地建议版冒称已生效。
4. 检查本次操作涉及的写入目标仅属于允许范围；若读取了其他岗位作对照，核对其可验证内容未改动。不为验收无依据扫描全部岗位或制造不存在的文档。
5. 下次执行读取该岗位最新确认 Prompt，并保存本批实际使用版本/规则快照。基础默认只用于新建初始化，不重叠加；发现旧 Prompt 未写全时停止受影响筛选并补齐，不静默从当前默认补值。
6. 汇报目标岗位、旧→新版本、实际修改项、回读结果和未完成项；明确不修改基础默认及其他岗位。不得把规则文字或静态审查当真实多岗位隔离已端到端验证。

## 最小验收场景

- 分别创建甲、乙，两份 Prompt 各自写全初始化标准且标识/文档独立。
- 修改甲的可配置通用项：只甲条目和甲版本变化，乙与基础默认保持原值。
- 再次运行甲、乙：各自读取各自最新确认版，不重新从基础默认覆盖。
- 临时改变甲本轮条件：只该批快照变化，甲持久版不变。
- 改基础默认后创建丙：丙采用新默认，甲/乙仍保留原独立版本。
- 无法明确目标、未决硬筛或写入失败：停止受影响部分，不跨岗位更新，不伪造持久成功。

上述是执行验收规范，不声明已存在数据库事务、自动同步服务或已完成真实多岗位测试。
